# 離線匿名化玩家資料

狀態：已接受（2026-09-28，Issue #25）

## 背景

`GLOSSARY.md` 的 Anonymized Player 必須保留 Invitation、Qualification、Reward 與稽核的歷史關係，但不能繼續以 Minecraft UUID、名稱或 IP 雜湊識別原玩家。現有三種 backend 的 `player_id` 都直接使用 Minecraft UUID，且 Reward、Audit 與自由文字欄位可能再次暴露身分。單純清空 `last_known_name` 不是匿名化。

## 已確認的產品決定

- 匿名化後，原玩家重新加入時視為全新玩家；舊 Minecraft UUID 不得再與歷史紀錄建立資料庫對應。
- 若相關 Reward Action 為 `PENDING`、`PROCESSING` 或 `UNCERTAIN`，拒絕匿名化，先由管理員依現有復原流程處理。
- 相關稽核原因與獎勵內容中的自由文字可以不可逆地遮蔽，但保留事件種類、狀態與時間。
- 以離線維護工具執行：先停止所有連至該 backend 的 InviteCode 實例並備份，不從遊戲中的 `/ic` 指令執行。

## 決定方案

維護工具在選定 backend 的單一交易中，為目標玩家產生隨機且未使用的歷史 UUID，重新指向所有歷史關係及獎勵收件者，刪除舊玩家主體、名稱、網路雜湊與登入日期。這個歷史 UUID 只供內部維持關聯；它不是新的 Minecraft 玩家 UUID。所有直接含有舊 UUID 或玩家名稱的相關文字須遮蔽或替換。既有 Reward 的冪等鍵與衍生識別碼也要檢查，避免可用已知 Minecraft UUID 反算；完成前不得開放服務。

管理員名稱可能出現在其他玩家的稽核或獎勵轉移紀錄；這些純文字操作者／原因會依名稱搜尋並遮蔽，不只依玩家外鍵選取。交易結束前檢查原 UUID 與名稱是否殘留於內部資料；若仍留在不可安全改寫的非關聯獎勵 payload 等欄位，整筆回滾並要求管理員先處理，以免影響其他玩家尚未交付的獎勵。

舊 Invite Code 必須失效，且不得再連到隨機歷史 UUID。為避免舊碼被重新發給其他玩家，以既有防濫用密鑰的獨立用途 HMAC 保存碼保留值，並在新碼產生時檢查；只有資料庫而沒有密鑰時，不應能有效枚舉短碼，保留值也不記錄原 Minecraft UUID。密鑰外洩時仍可能枚舉，須與資料庫分開保護。這需要明確的 SQLite／MySQL schema 版本與 JSON 格式處理，既有資料只走明確 migration。

工具先唯讀預檢：backend 與版本、密鑰、目標玩家、所有關聯及未完成獎勵；執行時再確認目的歷史 ID 不存在，並顯示將變更的資料範圍。只有管理員明確提供指定 UUID、停止所有實例及備份確認才執行。稽核事件採固定的隱私請求理由，不在資料庫保存可能重新識別玩家的自由文字原因。失敗或中斷時，交易回滾且來源可重試；若回滾狀態無法判斷，停止並要求檢查，不自動再次執行。JSON 必須沿用其原子快照寫入與前一份資料備份。

## 驗證界線

自動化驗證要檢查三個 backend 的歷史關係、名稱／網路雜湊移除、舊 UUID 不可查、新登入建立新玩家、舊碼不可再 Claim 或重新分配、Reward 狀態與時間保留，以及冪等鍵重建後仍保持唯一；另測故障回滾、並行維護工具、JSON 重啟與工具只接受明確目標。不使用正式玩家資料。MySQL 整合案例需要隔離的 8.4 測試服務，沒有該環境時不得把跳過誤報為通過。

匿名化不能抹去既有備份、伺服器 log、第三方插件或玩家自行保存的截圖／聊天紀錄；維運文件須說明備份保留及外部資料的獨立處理。保留精確的歷史時間與關係，也可能讓持有外部對照資料的人推測身分，不能宣稱絕對不可識別。
