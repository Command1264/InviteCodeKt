# 指令回饋、messages 與 prefix 待討論項目

狀態：2026-10-18 整體規格已確認通過，包含 console 16 色、不額外套粗體。第一、二階段已授權實作，詳見 [顯示規格](command-feedback-display-spec.md) 與 [第二階段證據](../testing/evidence/2026-10-18-command-feedback-stage2.md)。F205 JAR 與既有真人驗收保持原版本綁定；第三、四階段尚未開始。以下各輪保留討論歷程，後續已確認的修訂優先。

## 已提出的需求

- 重新討論指令回饋的顯示方式與排版，更新 `messages` 文字。
- 每個訊息前面都要有 prefix；實際內容、顏色與可設定方式待討論。
- 此前已提出的排版／美術改善一併檢視，保留邀請碼直接點擊複製、懸浮提示與確認互動。

## 定稿前需要明確的部分

1. prefix 的文字、顏色與語系設定位置；例如是否採 `[InviteCode]`，目前只是候選，不當成已選定。
2. 成功、錯誤、提醒、help、status／stats 的文字層級與多行排版；多行訊息是整段一次 prefix，或每行都有 prefix。
3. 「每個訊息」如何涵蓋聊天、console、Dialog 內文／標題、按鈕與懸浮提示；須先列出顯示項目讓使用者確認，不自行刪減 prefix 需求或在每個按鈕硬加字樣。
4. 玩家與 console 的顯示差異、繁中／英文的一致性，以及玩家自訂 messages 的設定升級方式。
5. prefix 只影響顯示文字；複製到剪貼簿的內容仍須是原始邀請碼，點擊執行的命令、HEX 色彩與期限判定不能被排版變更破壞。

建議的第一個行動：盤點現有訊息，提供「成功、拒絕、確認」三種靜態樣例，再討論上列規則。此為建議，不表示已批准特定設計、建立 GitHub issue 或開始改程式。

定稿後才建立／更新經授權的 GitHub issue，依本機 develop 狀態與候選依賴選擇分支，實作後補足舊版聊天、新版 Dialog、console 與複製／點擊互動的必要驗證。顯示修改若形成新 JAR，舊 F205 的真人結果保留原版本綁定。

## 第一輪討論（前三項已確認）

關服終端機例外依使用者要求先保留紀錄，暫不修復、不做隔離測試；本輪只討論顯示設計。

### 現況與限制

- 一般指令、help 指令列、管理查詢、互動聊天、Dialog 與 MESSAGE 獎勵各有輸出路徑。未來實作不能只修改一般 send 入口。
- `value.yes/no` 等是組合回覆的值；不能在語系解析器替每個鍵無條件加 prefix。
- 建立邀請關係不等於達成資格；達成資格也不等於獎勵已成功發送。
- 保留邀請碼 HEX 色彩、直接點擊複製、hover、同意／不同意與 60 秒期限。複製內容與點擊命令不包含 prefix。
- Dialog 按鈕底色由客戶端控制，設計不承諾可任意更改。舊版不保證呈現 HEX 顏色。

### 建議方向

1. prefix 使用可設定的 `[InviteCode]`。預設灰色括號、金色產品名稱；成功綠色、提醒黃色、拒絕紅色，但仍以文字說明結果。
2. 聊天與命令 console 每則完整回覆標示一次；多行回覆只在首行放 prefix。Dialog 在標題標示產品名稱。按鈕、hover、欄位名稱與值不各自重複標示。這是對「每個訊息」的建議解讀，須由使用者確認，尚未定案。伺服器 logger 已有插件標識，避免重複。
3. 玩家先看結果，再看原因與可行的下一步；管理員 console 保留診斷欄位。只有確實可行的操作才給建議，不能要求已失去資格的玩家再換碼重試。
4. prefix 集中設定，不要求維護者手動貼在每個 messages 鍵上；具體配置位置、可否留空與升級方式留待後續討論。

### 第一輪問題

1. 是否接受上述 prefix 範圍：一則回覆一次、多行首行一次、Dialog 標題標示，按鈕／hover／值不另加？
2. 是否接受預設 `[InviteCode]` 灰括號與金色名稱，並可自訂？
3. 是否接受玩家用白話的「結果 → 原因／下一步」，管理員輸出保留必要診斷資料，並將成功／提醒／拒絕分色？

使用者後續回覆「三題都依妳建議」：上述問題 1–3 已確認。建議方向 1–3 為顯示規格決定；第 4 項的配置細節仍待確認。這不是程式修改或 remote write 授權。不新增 ADR 或改寫領域詞彙。

## 第二輪討論（已確認，確認區與缺檔行為追加調整）

4. **Help**：每行「指令 — 簡短用途」，沿用依權限及玩家／console 身分篩選；有權限的管理員分「玩家操作／管理操作」，console 不列玩家專用指令。不新增路由或分頁。玩家點擊只填入聊天列，不立即執行，避免誤觸建立邀請碼而失去 claim 資格。完整管理用法須與既有 parser 對應，不以省略號代替正式參數說明。
5. **Status／stats**：status 回答自己的登記狀態與待補發筆數，stats 回答作為邀請人的人數統計；每欄一行。沿用現有欄位，不新增排行榜、獎勵金額或資格進度百分比。若不能登記，顯示可取得的實際原因；原因未能判定時不猜測，須在實作前核對資料路徑。
6. **確認畫面**：標題 `[InviteCode] 確認邀請碼`，其後依序邀請人、邀請碼、確認問題、`請在 {seconds} 秒內選擇`、同意／不同意。末句不加冒號，不新增每秒重繪或聊天倒數洗版；依現有機制逾時失效，使用過期操作時說明重新開始方式。聊天按鈕保留 hover 與直接操作，Dialog 使用等價內容與可支援的文字顏色，底色由客戶端控制。
7. **設定位置與文字形式**：建議 prefix、訊息及其顏色放在各語系 messages 檔；config.yml 只保留語系選擇等行為設定。插件自動加 prefix，不要求每句手貼。多行先用 YAML `|-` 字串，不引入陣列或可執行的格式語法；prefix 是否允許空值、顏色語法與按鈕樣式鍵留待此項接受後確認。沿用既有 JAR 與執行期設定檔路徑。
8. **設定更新**：建議保留管理員自訂內容，新增缺鍵時用同語系內建預設作最後備援並記錄可操作提示；不默默重寫 YAML。客戶端語系→設定預設語系的既有選擇規則保留，各語系都須先有完整內建樣板。舊檔在本輪若不需破壞性格式變更，不只因文案修改而升 messages-version；若最終配置契約確實不相容，再明確設計版本處理。reload 仍需整份驗證成功後一次套用，失敗保留舊設定。此為新提案，現況缺鍵仍回傳 `[missing: key]`，不能宣稱已有內建備援。

預覽用的 status：

```text
[InviteCode] 我的邀請狀態
可使用邀請碼：否
邀請關係：等待達成資格
待補發獎勵：0 筆
```

預覽用的 stats：

```text
[InviteCode] 我的邀請統計
等待達成資格：2 人
已達成資格：5 人
```

以上數字是樣例。status 原因與完整管理用法須在實作前補齊對應證據，不新增未驗證的獎勵成功敘述。

使用者回覆「4–8 都依妳建議」，並追加兩項要求：確認區 prefix 獨立第一行、後面不留空格，其他內容放第 2–7 行；確認畫面希望置中。缺少檔案時須從 JAR 複製初始檔案。舊的同列確認標題樣例由下列第三輪草案取代，對齊範圍仍需確認。

## 第三輪討論（已確認，console 色彩另行修訂）

9. **七行確認區與對齊範圍**：建議第 1 行只有 prefix，第 2 行「確認邀請碼」，第 3–6 行依序為邀請人、邀請碼、問題、期限，第 7 行按鈕。聊天仍靠左，原生 Dialog 以 prefix 作標題、其他內容置中；使用者若也希望聊天置中，需另確認客戶端寬度與字型限制，不用固定空格假裝精準置中。各平台的置中 API 與實際客戶端外觀需在實作階段核對，目前 adapter 沒有明確設定對齊。Dialog 的「七行」是七個邏輯區塊，不保證自訂長文字在窄視窗仍只有七個實際文字行。
10. **prefix 配置鍵**：建議各語系用 `presentation.prefix: "&7[&6InviteCode&7]&r"`，值不含尾端空格。一般同列回覆由 renderer 加一個分隔空格；確認區獨立行不加。建議允許 `""` 關閉 prefix，並省略其分隔空格與獨立空行；這需要有別於現行所有鍵不得空白的解析規則。Dialog 標題不能依賴空 prefix 保持可識別性，關閉時以「確認邀請碼」作標題且不重複內文標題。
11. **顏色語法**：建議支援 `&0`–`&f`、`&k`–`&o`、`&r` 與單一 HEX 寫法 `&#RRGGBB`。先不引入 MiniMessage、漸層或新增套件；未支援的文字視為原文。支援 RGB 的平台呈現 HEX，舊版用既有最近基本色策略；console 命令回覆移除樣式碼，伺服器 logger 另循既有規則。模板先解析樣式再插入玩家輸入等動態值，避免名稱／外部文字被當成格式指令；複製及 click payload 始終不帶樣式。此為待實作契約，不是聲稱現有 messages 已支援上述語法。
12. **完整繁中文案方向**：見 [繁中完整訊息草案](command-feedback-messages-zh-TW.draft.yml)。保留既有鍵與變數，更新白話敘述；新增 prefix 與 help 說明鍵。建立關係、達成資格、獎勵已交付不能混稱。資格通知維持「已達成資格」，不聲稱所有獎勵已入帳。診斷識別符保留原文。建議以此為基礎，繁中與英文同步維護；英文完整對照在繁中內容確認後產生。
13. **缺檔復位時機與邊界**：已接受「缺檔從 JAR 補回、不覆寫既有檔案」。建議啟動及 `/ic reload` 載入前皆執行，僅針對 JAR 內建設定檔白名單；不把缺少自訂語系或損壞的 YAML 視為可任意重設。無法寫入、資源缺失或設定無效時明確報錯；reload 保留最後有效設定。資料庫與 anti-abuse key 不屬於此設定檔復位規則，不藉此重建任何既有資料或金鑰。

第三輪確認後仍需核對完整 help 用法與英文文案，再讓使用者確認整體規格，方可提出程式實作計畫。本輪只更新設計文件與離線預覽，沒有建置、部署或變更已驗收 JAR。

## 整體審閱稿

使用者已接受第 9–13 項，明確指定聊天靠左、Dialog 置中；並撤換原先 console 純文字方向：console 希望保留玩家相同的色彩語意，玩家專用指令才拒絕，要求評估粗體與 HEX 的能力／黑底可讀性。

已完成 [完整 help 用法核對](command-feedback-help-reference.md) 與 [英文完整文案](command-feedback-messages-en-US.draft.yml)。繁中與英文保留全部既有訊息鍵及變數；help 用途依 20 個 parser route ID 補齊。新增「此指令只能由玩家執行」的對等文字，不因 console 而拒絕管理命令。

最後建議的 console 策略為：保留成功／警告／錯誤色彩，預設 16 色、不額外套粗體，HEX 選最近基本色並避開過暗結果；不引入 HEX 偵測或終端依賴。終端能力與實際主題不保證相同，此建議及完整整合稿仍待使用者最後確認。以 [整體規格](command-feedback-display-spec.md) 為本輪審閱依據，不將原先「移除全部色碼」歷史提案當成現行要求。
