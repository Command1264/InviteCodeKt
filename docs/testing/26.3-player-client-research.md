# Minecraft Java 26.3 玩家客戶端自動化上游調查

調查日期：2026-10-15（Asia/Taipei）

後續結果：同日使用者已確認固定 F205 JAR 在 Paper 26.3 build 184 的完整真人清單通過，見 [驗收紀錄](evidence/2026-10-15-paper263-human-acceptance.md)。下列 client 調查仍是自動化能力的歷史截點；Spigot 26.3 玩家流程未因此通過。

## 結論

截至調查日，未找到可依賴的、已維護且已發行的 26.3 完整玩家自動化客戶端。PrismarineJS 的 Mineflayer 生態仍在積極補上 26.3 支援，但核心資料與 Mineflayer 修正尚有多個未合併 PR；版本 metadata 出現 `26.3` 不能證明客戶端已能通過登入、遊戲封包交換與持續操作。Complexity-ML 的發行版明確鎖定 26.2，也不能作為 26.3 玩家客戶端。

此判定限於下列指定官方 GitHub repository、release 與 issue／PR 狀態，不代表不存在其他未列入範圍的私人或非官方客戶端。

## PrismarineJS 上游

### `minecraft-data`

主線 `data/pc/common/protocolVersions.json` 已列出 `26.3`、協定版本 `777`、資料版本 `5023`。這只是版本索引：同一 repository 的 `data/pc` 目錄目前沒有 `26.3` 資料目錄；提供完整 Java 26.3 資料的 [PR #1300](https://github.com/PrismarineJS/minecraft-data/pull/1300) 及後續協定修正 [PR #1301](https://github.com/PrismarineJS/minecraft-data/pull/1301) 在查核時都仍為 open，沒有合併。主線索引所在的 Git blob 為 `939de6d17f1b6c8c8959fbf994f76e5a37b5fbc7`；repository HEAD 為 `201ca802a1b2c968b02e7fa5b31dd74e8bff3d8b`（2026-10-13，加入 26.4 snapshot 版本）。

因此，應把「可辨識版本字串／協定號」與「套件內已有可供序列化、解碼及遊戲狀態處理的 26.3 資料」分開。PR 的分支變更不能當成已發布套件的能力。

### `node-minecraft-protocol`

該專案是封包序列化與連線協定層，不是完整玩家自動化客戶端。其主線 HEAD 為 `1c83189272348b9e12076465a748a5ecdd14acce`（2026-10-03）；該提交修的是 26.2 伺服器端 login success 的 `sessionId` 欄位，提交說明明確指出這是供自架伺服器使用的伺服器端修正，並提及當時正在讓 26.2 `minecraft-data` 串接工作。已查的上游 release／README 沒有已發布的 26.3 完整客戶端宣告。

來源：[主線提交](https://github.com/PrismarineJS/node-minecraft-protocol/commit/1c83189272348b9e12076465a748a5ecdd14acce)、[README 支援版本說明](https://github.com/PrismarineJS/node-minecraft-protocol/blob/master/docs/README.md)、[上游 releases](https://github.com/PrismarineJS/node-minecraft-protocol/releases)。

### `mineflayer`

Mineflayer 才是高階玩家自動化 API；其上游 release 頁面最新正式標籤為 `4.39.0`，提交 `c168635cf2f6602069fc5e408bec864702335581`，發行日期 2026-09-06。主線 HEAD 為 `7b4bb8d2b56be9cdb832474af873acd37e609746`（2026-10-10）。截至調查日，重要 26.3 支援工作仍未合併：

- [PR #4124「26.3」](https://github.com/PrismarineJS/mineflayer/pull/4124)，HEAD `78424bf5abf0f351b1a3751b2f8e0423ab54b350`，仍 open；PR 自述只是 26.3 的 boilerplate，並指向尚未合併的 `minecraft-data#1300`。
- [PR #4130](https://github.com/PrismarineJS/mineflayer/pull/4130)，HEAD `93c7143c74afb42bffab553106147697c557d39f`，仍 open。說明記錄 26.3 的 `accept_teleportation` 新增位置與旋轉欄位；缺少欄位會序列化成 NaN，玩家在登入進入遊戲後便遭伺服器踢出。雖然 PR 作者回報在 Paper 26.3 上可登入、收取區塊並移動數分鐘，這是未合併分支的測試證據，不是正式發行版支援。
- [PR #4144](https://github.com/PrismarineJS/mineflayer/pull/4144)，HEAD `fddece587e865c8f8c77b9f2fb887f8302ae5884`，仍 open，處理新的 entity-move／position-sync delta 格式。
- [PR #4146](https://github.com/PrismarineJS/mineflayer/pull/4146)，HEAD `651195051e539c7737397b1c1167c882848031f3`，仍 open，修正 26.3 改動後的 digging／release-held-item action ID。
- [PR #4137](https://github.com/PrismarineJS/mineflayer/pull/4137) 已於 2026-10-03 合併，補上 `tick_end`；單一封包修正已落地，仍不足以代表整條 26.3 協定與遊戲狀態路徑完成。

另見 [Mineflayer 主線提交](https://github.com/PrismarineJS/mineflayer/commit/7b4bb8d2b56be9cdb832474af873acd37e609746)、[正式 releases](https://github.com/PrismarineJS/mineflayer/releases) 及 [上游 26.3 PR 搜尋結果所列工作](https://github.com/PrismarineJS/mineflayer/pulls?q=is%3Apr+26.3)。

## Complexity-ML `mineflayer-26.2`

這是獨立下游發行版，README 明確限定 Minecraft Java 26.2／協定 776，並指出需要配套的 26.2 protocol、data、chunk、physics 套件。其最新 release 為 `complexity-26.2.3`（2026-07-27），提供完整 Mineflayer 功能與 26.2 的測試／實服 spawn 敘述；repository 主線 HEAD `5662305a63c1f60df869a95c19b4715d11c38497`。README 也說明它不是 PrismarineJS 官方發行版。以上均支持其 26.2 定位，沒有 26.3 支援證據。

來源：[repository README](https://github.com/Complexity-ML/mineflayer-26.2)、[26.2.3 release](https://github.com/Complexity-ML/mineflayer-26.2/releases/tag/complexity-26.2.3)、[主線提交](https://github.com/Complexity-ML/mineflayer-26.2/commit/5662305a63c1f60df869a95c19b4715d11c38497)。

## 建議的最低可行驗證

建議以官方 26.3 Java 用戶端補測，不必等機器人套件更新，也不為此自行拼接多個未合併上游 PR。對象為固定 F205 `InviteCode-1.0.0.jar`；Paper 26.3 build 184 與 Spigot 26.3 build 4663 各自記錄結果。以下是待準備的測試方案，尚未建立新 Human 實例或交付可登入入口。

先為兩種核心安排新的獨立測試資料與未占用 port；不升級或覆寫既有 Human 世界。只有本次專用設定可將相同 IP 規則設為 `ALLOW`，以便同一台電腦的兩個帳號測試；不變更既有測服的防濫用政策。設定、JAR／核心雜湊與資格／獎勵條件須先記錄，再提供實際登入方式。

每種核心的最小完整清單：

1. 帳號 A 登入，執行 `/ic code`。記錄邀請碼；滑鼠懸浮與點擊複製應可用。
2. 帳號 B 執行 `/ic claim`。應出現原生輸入畫面；填入 A 的碼，核對邀請人與確認摘要。先按「不同意」，`/ic status` 應沒有邀請關係。
3. B 再提交相同碼並按「同意」。狀態應有正確邀請人；再次 `/ic claim` 應立即拒絕，不進入輸入流程。資格條件先保持未達成，便於測試下一步。
4. 正常 `stop` 後重啟。B 的邀請關係與尚未達成的資格狀態應保留，SQLite 與 anti-abuse key 不應重建。
5. A 離線後，讓 B 達成本次已記錄的資格條件。用 console 的 `ic admin doctor` 核對 A 的待發獎勵，正常停止並重啟，再核對待發狀態仍保留。A 再登入應收到一次預定獎勵；以訊息／實際獎勵效果及 `/ic stats` 核對，不只看 log。
6. 再正常停止、重啟與登入。關係／資格／統計應保留，獎勵不得重複發送。保存核心與插件雜湊、實際步驟、結果、錯誤 log；兩種核心分別回報「全部通過」或失敗步驟與畫面。

這份清單補上新版本的玩家、Dialog、離線獎勵與重啟路徑；既有逾時、防濫用與管理員復原證據仍各自保存。原生 Dialog 的按鈕底色由 client 控制。通過後仍須處理歷史真人證據沿用判定與產品／第三方授權，才具備完整發行條件；測試通過不授權 push 或發布。

## 本機正向對照

同日以現有 lockfile 安裝的套件離線建立 PLAY 封包編碼器：`26.1` 成功，`26.3` 失敗並回報 `No data available for version 26.3`。已保存 `artifacts/release-1.0.0-20261015/client-capability-recheck.json`，包含套件版本、Node 版本與 lockfile SHA-256。未發出網路登入；因此這份結果只證明目前 client 缺少所需資料，不能當作插件或伺服器相容性失敗。

若目前無法操作官方用戶端與 26.3 測服，最低替代只能是保留已通過的自動化證據，並把 26.3 玩家流程明確標為未驗證／待人工驗收；不要以 `protocolVersions.json` 有版本項目、26.2 下游套件、連線 handshake 或未合併 PR 的成功回報推定完整 26.3 支援。

## 查核邊界

查核透過官方 GitHub repository、主線檔案與 commit、release、pull request 狀態及 PR 內測試說明完成；沒有安裝依賴、執行客戶端、啟動伺服器或修改遠端內容。上游會持續變動，本文狀態只代表 2026-10-15 的查核截點。
